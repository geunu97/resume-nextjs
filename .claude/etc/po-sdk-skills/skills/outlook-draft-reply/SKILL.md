# Outlook 답장 초안 저장

완성된 답장 문구를 원본 메일에 대한 "답장" 형태로 Outlook Drafts 폴더에 저장합니다. 발신인, 제목(RE:), 스레드 인용 내역이 실제 답장처럼 자동으로 붙고, 저장만 될 뿐 절대 발송되지 않습니다.

## 언제 쓰는지

- `sdk-license-notice`, `vendor-mail-reply`, `vendor-repro-request` 등 메일 문구 작성 스킬이 끝난 뒤, 그 결과물을 그대로 임시보관함에 넣어달라고 할 때.
- 사용자가 직접 준 문구를 특정 메일에 대한 답장 초안으로 저장해달라고 할 때.

## 확인 순서

### 1. 원본 메일 식별

- 지금 대화 중에 이미 참조/확인된 원본 문의 메일이 있으면 그 메일을 그대로 사용합니다 (messageId 확보 — 다시 검색하지 않음).
- 없거나 어떤 메일인지 애매하면 사용자에게 발신자·제목 등으로 어떤 메일에 대한 답장인지 확인합니다. **임의로 아무 메일이나 골라 답장하지 않습니다.**
- 사용자가 "답장 말고 새 메일로 만들어줘"라고 명시하면 `create-draft-email`로 새 메일 초안을 만들고, 이때는 받는사람(to)을 반드시 물어봅니다 — 추측해서 채우지 않습니다.

**내부 전달 메일 판별 (중요):** 이 사서함에는 영업팀 담당자(예: Reno)가 고객사의 원문의를 사내 공유메일함(`weboffice@polarisoffice.com`, `sales@` 등)으로 "FW:"로 전달한 메일이 자주 들어옵니다. 식별한 원본 메일이 이런 **내부 전달 메일**인지 먼저 확인합니다 — 발신자가 `@polarisoffice.com` 사내 계정이고, 본문에 실제 고객사 담당자가 보낸 원문이 인용되어 포함돼 있으면 내부 전달 메일입니다.

- **내부 전달 메일인 경우**: 이 메일에 그대로 답장(`create-reply-draft`/`create-reply-all-draft`)하면 안 됩니다 — 받는사람이 전달해준 사내 담당자(예: Reno)가 되어 정작 고객사에는 전달되지 않습니다.
  - 인용된 본문에서 **실제 원 발신자(외부 고객사 담당자)**의 이메일을 찾아, 그 사람을 받는사람으로 하는 새 메일 초안(`create-draft-email`)을 만듭니다.
  - 참조(cc) 후보는 전달해준 사내 담당자(Reno 등)와, 인용된 원본 메일에 있던 고객사 측 cc 목록에서 뽑되, 확인 방식은 아래 "받는사람/참조 확인 방식"을 따릅니다.
  - 제목은 인용된 원본 메일의 제목을 기준으로 `RE:`를 붙입니다 (내부 전달 메일 자체의 "FW:" 제목이 아님).
- **고객사 담당자로부터 직접 온 메일인 경우** (내부 전달이 아닌 경우): 그 메일에 그대로 답장합니다 — 아래 수신 범위 규칙을 따릅니다.

### 2. 수신 범위 (답장 vs 전체 답장)

이 단계는 원본 메일이 **내부 전달 메일이 아닌 경우**에만 적용됩니다 (내부 전달 메일이면 위 규칙대로 `create-draft-email`로 새로 만듭니다).

- 원본 메일에 참조(cc) 대상이 있으면 기본으로 전체 답장(`create-reply-all-draft`)을 후보로 삼습니다.
- 참조가 없으면 단순 답장(`create-reply-draft`)을 사용합니다.
- 실제 수신자 확정은 아래 "받는사람/참조 확인 방식"을 따릅니다.

### 2-1. 받는사람/참조 확인 방식 (한 번에 몰아서 묻지 않음)

받는사람/참조 후보를 표 하나로 몰아서 보여주고 "이대로 저장할까요?"라고 한 번에 확인받지 않습니다. 대신 아래 순서로 하나씩 물어봅니다.

1. **받는사람(to) 먼저 확인**: "받는사람은 OOO(이메일)로 할까요?" 하나만 묻습니다.
2. **참조(cc) 후보를 한 명씩 확인**: 후보가 여러 명이면 "참조에 OOO(이메일)도 넣을까요?" 형태로 후보 한 명당 하나씩 물어봅니다 — 후보 전체를 한 번에 나열해서 예/아니오로 묻지 않습니다.
3. **후보를 다 확인한 뒤에는 더 추가할 사람이 없는지 물어봅니다**: "이 외에 받는사람이나 참조에 추가하실 분 있나요?"
4. 위 과정에서 확정된 목록으로만 실제 저장 호출을 합니다.

**`create-draft-email` 호출 시 주의**: `subject`/`toRecipients`/`ccRecipients`/`body`를 도구 호출의 최상위 파라미터로 넣으면 `400 Bad Request`(스키마 불일치)가 납니다. 전부 `body`라는 하나의 객체 파라미터 안에 중첩해서 넣어야 합니다 — 예: `{"body": {"subject": "...", "toRecipients": [...], "ccRecipients": [...], "body": {"contentType": "text", "content": "..."}}}` (바깥 `body`는 도구 파라미터, 안쪽 `body`는 메일 본문).

### 3. 본문 삽입

- 요청 바디의 `comment` 필드를 사용합니다 (`Message.body` 아님) — 이렇게 해야 우리가 쓴 문구 아래에 원본 스레드 인용 내용이 자동으로 붙어서, 실제로 발신했던 과거 메일들과 같은 형태가 됩니다.
- **`comment` 값은 일반 텍스트가 아니라 HTML 조각으로 그대로 삽입됩니다.** HTML에서는 소스상의 줄바꿈(`\n`)이 렌더링 시 무시되고 공백으로 합쳐지므로, 문구에 있는 줄바꿈을 그대로 `\n`으로 넣으면 Outlook에서 전부 한 줄로 붙어버립니다(2026-08-04 실제 발급 후 확인된 문제). **반드시 각 줄바꿈을 `<br>`로 치환한 뒤 `comment`에 넣습니다** (예: 문단 사이 빈 줄은 `<br><br>`). 문구 내용 자체는 요약하거나 재작성하지 않고, 줄바꿈 표현 방식만 `<br>`로 바꿉니다.
- 전달받은 문구는 그대로 넣습니다 — 요약하거나 재작성하지 않습니다.
- 제목은 건드리지 않습니다 (Graph가 자동으로 `RE:` 처리).

### 4. 인용된 스레드 히스토리 내 민감정보 확인

- 답장/전체답장 저장 시 원본 메일의 스레드 히스토리(이전 주고받은 내용)가 자동으로 본문 아래에 인용되어 붙습니다. 이 인용 내역을 살펴보고, **사내 담당자끼리만 주고받은 내용(예: 견적가/단가, 데모 사이트 계정·비밀번호, 내부 검토 코멘트, 이번 수신자가 원래 포함되지 않았던 사내 전용 회신 등)이 포함돼 있으면 반드시 사용자에게 알립니다.**
- "이 초안은 저장만 됐고, 실제 발송 전에 임시보관함에서 인용된 이전 내용 중 OO(구체적으로 어떤 내용인지) 부분을 삭제하고 보내시는 걸 권장드립니다" 형태로 구체적으로 안내합니다. 이 스킬이 임의로 인용 내역을 잘라내거나 수정하지는 않습니다 — 안내만 하고 실제 편집은 사용자가 Outlook에서 직접 합니다.
- 민감정보로 보이는 내용이 없으면 이 안내는 생략해도 됩니다.

### 5. 첨부파일(라이선스 키 등) 확인

- 이 대화에서 방금 발급/확인된 라이선스 키나 별도로 전달할 라이선스 키가 있으면, 이를 파일로 첨부할지 사용자에게 먼저 물어봅니다. 임의로 첨부하지 않습니다.
- 첨부하기로 하면 파일명도 반드시 사용자에게 물어봅니다 (임의로 정하지 않음, 확장자는 `.txt` 기본값으로 제안 가능).
- 첨부는 `add-mail-attachment`로 저장된 초안(draft) 메시지에 대해 진행합니다 — `contentBytes`는 파일 내용을 base64로 인코딩해서 전달합니다.

### 6. 저장 후 확인

- 임시보관함에 저장됐다는 것과, **자동으로 발송한 게 아니라는 것**을 사용자에게 명확히 알립니다.
- Outlook 답장 초안은 메일함 기본 서식(HTML)에 따라 `comment`의 줄바꿈/간격이 원래 텍스트와 다르게 보일 수 있습니다 — 처음 사용할 때는 실제 Outlook에서 초안을 열어 서식(특히 문단 간격)이 의도대로 보이는지 한 번 확인해보시길 권장한다고 안내합니다.

## 절대 하지 말 것

- `send-mail`, `send-draft-message` 등 발송 관련 도구는 절대 호출하지 않습니다 — 이 스킬은 저장까지만 합니다.
- 받는사람(to)/참조(cc)를 사용자에게 보여주고 확인받기 전에 바로 저장하지 않습니다.
- 받는사람/참조 후보를 한 번에 몰아서 나열하고 "이대로 저장할까요?" 하나로 퉁쳐서 묻지 않습니다 — 받는사람 → 참조 후보 한 명씩 → 추가할 사람 있는지, 순서대로 하나씩 물어봅니다.
- 전달받은 본문 문구를 임의로 요약·재작성하지 않습니다 — 그대로 사용합니다.
- 원본 메일이 명확하지 않은데 임의로 아무 메일이나 골라 답장하지 않습니다.
- **내부 전달 메일(사내 담당자가 고객 문의를 사내 공유메일함으로 FW한 메일)에 그대로 답장하지 않습니다** — 받는사람이 고객이 아니라 전달해준 사내 담당자가 되어버립니다. 인용된 원 발신자를 찾아 새 메일로 만듭니다.
- `comment` 필드에 줄바꿈을 `\n`으로만 넣지 않습니다 — HTML로 삽입되어 전부 한 줄로 붙어버립니다. 반드시 `<br>`로 치환합니다.
- 인용된 스레드 히스토리에 견적가·데모 계정정보 등 사내 전용/민감 내용이 보이는데도 이를 사용자에게 안내하지 않고 그냥 저장만 하고 끝내지 않습니다.
- 라이선스 키 등 첨부 여부를 묻지 않고 임의로 첨부하거나, 반대로 첨부가 필요할 수 있는 상황인데 묻지 않고 넘어가지 않습니다. 파일명도 반드시 사용자에게 확인합니다.

## 다른 스킬과의 연계

`sdk-license-notice` 등 메일 문구 작성 스킬이 완성된 문구를 저장한 뒤 "이 문구를 Outlook 임시보관함에 답장 초안으로 저장해드릴까요?"라고 물어보고, 사용자가 원하면 이 스킬로 넘어옵니다. 이때 그 스킬에서 이미 확인된 원본 메일과 완성된 문구는 다시 묻지 않고 그대로 사용합니다.
