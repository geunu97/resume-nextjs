# SDK 라이선스 API 직접 발급

sdkbuilder Back Office의 "라이선스만 발급" 기능과 동일한 API를 curl로 직접 호출해서 라이선스를 발급하는 스킬입니다. 실제로 되돌리기 번거로운 데이터(라이선스 발급 이력)를 생성하는 작업이므로, 항목 확인 → 최종 확인 → 호출 순서를 반드시 지킵니다.

## 배경 (2026-08-04, JS 번들 정적 분석 기준 — API 스펙이 바뀌면 재확인 필요)

- Base URL: `http://sdkbuilder.polarisoffice.com` (사내망 전용 도메인, HTTP, 인증 없이 GET 호출되는 것까지 확인됨)
- 관련 API
  - `GET /api/v1/SDKlicenseBuilder/getAllDeployInfo` — 전체 발급 이력 조회 (인증 불필요 확인됨)
  - `GET /api/v1/SDKlicenseBuilder/getOneDeployInfo?id={id}` — 단건 조회
  - `GET /api/v1/SDKlicenseBuilder/getTagList` — SDK 버전 태그 목록 (이 스킬에서는 사용 안 함, 아래 참고)
  - `POST /api/v2/SDKlicenseBuilder/generateLicense` — **실제 라이선스 발급 API** (이 스킬이 호출하는 대상)
- `generateLicense` 요청 바디 (JS 소스에서 확인됨):
  ```json
  {
    "company": "",
    "expiryDate": "",
    "domain": "",
    "format": "",
    "description": "",
    "tagName": "",
    "tagId": "",
    "isViewer": false,
    "isEvaluation": false,
    "isCreateJiraIssue": false,
    "isThread": false,
    "publicURL": "",
    "note": ""
  }
  ```
  - "라이선스만 발급" 모드는 빌드/배포를 하지 않는 모드라 `tagName`, `tagId`, `publicURL`은 빈 문자열(`""`)로 보냅니다 (UI에서도 이 모드는 publicURL 입력이 비활성화되어 있고, 실제 발급 이력 데이터도 대부분 이 값들이 비어 있음).
  - `isCreateJiraIssue: true`로 보내면 백엔드가 알아서 Jira 이슈를 생성해주는 것으로 보입니다 — 이 스킬에서 별도로 Jira MCP를 호출할 필요는 없습니다.
- 인증: GET은 토큰 없이 호출되는 것을 확인했습니다. POST(`generateLicense`)는 실제로 호출해서 검증한 적이 아직 없으니, 401/403 등 인증 오류가 나면 **우회를 시도하지 말고** 사용자에게 알리고 중단합니다 (브라우저 로그인이 필요해졌을 수 있음).

## 절차

### 1. 회사명 확인

라이선스를 발급할 회사명을 사용자에게 묻습니다.

### 2. 관련 이력 조회

`GET /api/v1/SDKlicenseBuilder/getAllDeployInfo`를 호출해서 전체 목록을 받고, `company` 값이 1번 회사명과 같거나 포함 관계인 항목을 `createdAt` 내림차순으로 **최대 10개**까지 골라 사용자에게 보여줍니다 (회사명 / 만료일 / 도메인 / 포맷 / 설명 / note / isJira / 발급일 정도를 표로 정리).

일치하는 이력이 없으면 그대로 알리고 신규 발급으로 진행합니다 (이 경우 3번의 각 항목은 전부 새로 받습니다).

### 3. 항목별 확인 — 반드시 하나씩, 순서대로

아래 항목을 순서대로 확인합니다. 관련 이력이 있으면 "가장 최근 이력 값 그대로 쓸지 / 바꿀지"를 물어보고, 없으면 새로 받습니다. **하나라도 사용자에게 묻지 않고 이전 값이나 추측값을 임의로 채우지 않습니다.**

1. **Company**
2. **라이선스 종류 (운영 / 개발)** — 반드시 물어봅니다. 이후 단계(만료일, 도메인)의 검증 규칙이 여기에 따라 달라집니다.
   - **개발 라이선스로 답한 경우, 추가로 "테스트 라이선스인지"도 반드시 물어봅니다.** 개발 라이선스는 (a) 정식 개발 라이선스와 (b) 3개월짜리 테스트 라이선스로 나뉘며, 만료일 규칙이 서로 다릅니다(아래 3번). 사용자가 먼저 "테스트 라이선스"라고 명시한 경우에도 이 질문은 생략하지 않고 그대로 확인합니다.
   - 이 답변들(운영/개발, 테스트 여부)은 Description에 포함시킵니다(아래 6번).
3. **Expiry Date**
   - **운영 라이선스인 경우**: "영구"라고 답하면 `{발급 연도 + 100}-12-31`로 변환합니다 (예: 2026년에 발급하면 `2126-12-31` — 실제 기존 이력 데이터에서 확인된 규칙). `YYYY-MM-DD` 형식으로 직접 답하면 그대로 사용합니다.
   - **개발 라이선스 - 테스트 라이선스인 경우**: 만료일은 **발급일로부터 3개월**로 고정합니다 (예: 발급일이 2026-08-04이면 `2026-11-04`). 계산한 날짜를 사용자에게 제시하고 그대로 진행할지 확인받습니다. 사용자가 3개월을 넘는 날짜를 요청해도 임의로 반영하지 말고, 테스트 라이선스는 3개월 정책이라는 점을 안내한 뒤 재확인합니다.
   - **개발 라이선스 - 테스트 라이선스가 아닌 경우(정식 개발 라이선스)**: 만료일을 "발급일로부터 1년" 또는 "올해 말(`{발급 연도}-12-31`)" 중에서 고를지, 아니면 직접 날짜를 줄지 물어봅니다. **다만 2100년을 넘을 수 없습니다.** 사용자가 "영구"라고 답하거나 2100년을 넘는 날짜를 요청하면, 개발 라이선스는 2100년을 초과할 수 없다는 점을 알리고 2100-12-31 이하의 실제 날짜를 다시 확인합니다.
4. **Domain**
   - 사용자가 도메인을 `http://`, `https://` 같은 프로토콜 접두어가 붙은 형태로 주더라도(예: 메일 원문에 URL 형태로 적혀 있는 경우), 실제 payload의 `domain` 값에는 **반드시 접두어를 제거한 호스트명만** 넣습니다 (예: `http://taco.thinkerit.co.kr` → `taco.thinkerit.co.kr`). 같은 호스트가 http/https 두 형태로 중복 등장하면 하나로 합칩니다. 기존 발급 이력의 domain 값도 전부 접두어 없는 형태(`115.89.221.210, localhost, 127.0.0.1`)인 것과 일치시키기 위함입니다.
   - **개발 라이선스인 경우 (테스트 여부 무관)**: Domain을 받은 뒤, `localhost`와 `127.0.0.1`을 포함시킬지 반드시 별도로 물어봅니다. 포함하기로 하면 사용자가 준 도메인 목록에 이 둘을 추가합니다 (이미 들어있으면 중복 추가하지 않음).
   - **운영 라이선스인 경우**: 별도 규칙 없이 사용자가 준 값 그대로 사용합니다 (접두어 제거 규칙은 동일하게 적용).
5. **Format** (`hwp`, `word`, `sheet`, `slide` 중 콤마로 구분)
6. **Description** — 2번에서 확인한 라이선스 종류를 포함해서 작성합니다("운영 라이선스" / "개발 라이선스" / "개발 라이선스(테스트)"). 추가로 덧붙일 설명이 있는지 물어보고, 있으면 이어 붙입니다 (예: `개발 라이선스(테스트) / 내부 QA용`).
7. **Note**
8. **Jira (Create Issue)** — true/false → `isCreateJiraIssue`

`isViewer`, `isEvaluation`, `isThread`는 사용자가 따로 언급하지 않으면 참고 이력의 값을 가져오거나(이력 없으면 전부 `false`), `tagName`/`tagId`/`publicURL`은 항상 `""`으로 둡니다. 이 값들도 4번 최종 확인 때 함께 보여줍니다.

### 4. 최종 확인 (필수, 생략 금지)

실제로 전송할 전체 JSON payload를 사용자에게 그대로 보여주고 발급 진행 여부를 최종 확인받습니다. **이 확인 없이 바로 API를 호출하지 않습니다.**

### 5. 발급 API 호출

**절대 `-d '{JSON}'`처럼 한글이 포함된 JSON을 커맨드라인 인자로 직접 넘기지 않습니다.** 이 환경(Windows + Git Bash)에서는 curl.exe가 네이티브 바이너리라 커맨드라인 인자가 콘솔 코드페이지(CP949 등)로 변환되면서 한글이 깨진 바이트로 전송되고, 그대로 서버에 저장되어 버립니다(표시 문제가 아니라 실제 DB에 깨진 텍스트가 저장됨 — 되돌릴 수 있는 수정/삭제 API가 없음).

반드시 아래 순서로 진행합니다:

1. Write 도구로 최종 JSON payload를 UTF-8 파일로 저장합니다(스크래치패드 디렉터리 사용, 예: `generate_license_payload.json`).
2. 그 파일을 `--data-binary @파일경로`로 전달합니다 (인자로 JSON을 직접 쓰지 않음):

```bash
curl -s -X POST "http://sdkbuilder.polarisoffice.com/api/v2/SDKlicenseBuilder/generateLicense" \
  -H "Content-Type: application/json; charset=utf-8" \
  --data-binary @"{scratchpad}/generate_license_payload.json"
```

3. 호출 직후 반드시 `GET /api/v1/SDKlicenseBuilder/getOneDeployInfo?id={응답의 id}`로 실제 저장된 값을 조회해서 회사명/설명 등 한글 필드가 깨지지 않았는지 확인합니다. 깨져 있으면(예: `�` 문자 포함) 절대 그대로 두지 말고 사용자에게 즉시 알립니다 — 수정 API가 없으므로 재발급 여부를 사용자와 논의해야 합니다.

- 401/403 등 인증 관련 오류가 나면 우회하지 말고 사용자에게 상황을 알립니다 (브라우저 로그인이 필요해졌을 가능성 등).
- 5xx 등 다른 오류가 나면 응답 내용을 그대로 사용자에게 보여줍니다.

### 6. 결과 보고

응답 내용(발급된 라이선스 키, 생성된 레코드 id 등)을 사용자에게 보여줍니다.

### 7. 안내 메일 작성으로 이어갈지 확인

결과 보고 후, **반드시** 이어서 안내 메일 문구도 작성할지 사용자에게 물어봅니다 (예: "이어서 안내 메일 문구도 작성해드릴까요? (`sdk-license-notice` 스킬)"). 단순 안내로 끝내지 않고 실제로 예/아니오를 확인받습니다.

- **아니오** → 그대로 종료합니다.
- **예** → `sdk-license-notice` 스킬로 전환합니다. 이때 방금 이 스킬에서 이미 확인한 값(회사명, 운영/개발 및 테스트 여부, Domain, Expiry Date, 다운로드 버전 등 겹치는 항목)은 `sdk-license-notice`의 확인 순서에서 처음부터 다시 묻지 말고, "방금 발급한 값 그대로 쓸지"를 먼저 제시해서 확인받는 방식으로 진행합니다(사용자가 다른 값을 원하면 그 값을 따릅니다). `sdk-license-notice`에는 없는 항목(예: 이전 버전 이력, 샘플 코드 포함 여부)은 그 스킬 절차대로 정상적으로 물어봅니다.

## 절대 하지 말 것

- 3번의 항목 중 하나라도 사용자 확인 없이 임의의 값으로 채우지 않습니다.
- 4번 최종 확인 없이 바로 API를 호출하지 않습니다 — 매번 실제 라이선스 데이터가 생성되는 액션입니다.
- 운영/개발 라이선스 여부를 묻지 않고 임의로 판단하지 않습니다.
- 개발 라이선스인데 **테스트 라이선스 여부를 묻지 않고** 만료일을 정하지 않습니다 — 테스트 여부에 따라 만료일 규칙(3개월 vs 1년/올해말, 2100년 상한)이 다릅니다.
- 테스트 라이선스인데 3개월을 초과하는 만료일로 임의로 진행하지 않습니다.
- 정식 개발 라이선스인데 만료일이 2100년을 초과하거나, Domain에 `localhost`/`127.0.0.1` 포함 여부를 확인하지 않고 그대로 진행하지 않습니다.
- Domain 값에 `http://`, `https://` 접두어를 그대로 남겨서 payload를 전송하지 않습니다 — 반드시 호스트명만 남기고 제거합니다.
- POST 호출이 인증 오류로 실패하면 다른 방식(토큰 추측, 헤더 위조 등)으로 우회를 시도하지 않고 사용자에게 알립니다.
- 한글이 포함된 JSON을 curl의 `-d`/`--data` 커맨드라인 인자로 직접 넘기지 않습니다 — Windows + Git Bash 환경에서 인코딩이 깨져 서버에 손상된 텍스트가 그대로 저장됩니다(수정 API 없음). 반드시 UTF-8 파일로 저장 후 `--data-binary @파일`로 호출하고, 호출 후 `getOneDeployInfo`로 실제 저장값을 재확인합니다.
- 발급이 끝났다고 바로 종료하지 않습니다 — 7번에서 안내 메일(`sdk-license-notice`)로 이어갈지 반드시 물어봅니다.
