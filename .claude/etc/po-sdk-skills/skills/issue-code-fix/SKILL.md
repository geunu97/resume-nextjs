# 이슈 기반 코드 수정 (Jira / 메일 공통)

Jira 이슈 또는 메일로 전달된 버그 리포트를 참고해서, 이 SDK 저장소(`polaris-weboffice/sdk`) 코드를 실제로 조사하고 고치는 스킬입니다. 입력 채널(Jira vs 메일)에 상관없이 동일한 절차를 따릅니다 — 채널별 포맷팅(제목 템플릿, 답장 톤 등)은 이 스킬의 관심사가 아닙니다.

## 다른 스킬과의 경계

이 저장소에는 "이슈"를 다루는 스킬이 여러 개 있어 혼동하기 쉽습니다. 아래 기준으로 구분하세요:

| 상황 | 스킬 |
|---|---|
| 실제로 코드를 조사/수정해야 함 | **이 스킬(issue-code-fix)** |
| 메일 문의에 답장 문구만 필요 (코드 변경 없음) | `vendor-mail-reply` |
| 메일을 WO Jira 티켓으로 등록만 하면 됨 | `mail-to-jira-issue` |
| 재현이 안 돼서 업체에 추가 정보를 요청해야 함 | `vendor-repro-request` |
| 엔진 C++ 소스 자체를 들여다봐야 함 (읽기 전용) | `engine-source-reference` (이 스킬 4단계에서 하위 도구로 사용) |
| 브랜치 생성/커밋/push/PR | `github-workflow` (수정 완료 후 사용자가 요청하면 별도로 이어서 사용) |

애매하면 사용자에게 "코드까지 고쳐드릴까요, 아니면 답장/티켓만 필요하신가요?" 하고 확인하세요.

## 워크플로우

### 1. 이슈 내용 확보

- **Jira 키/URL로 지목** (예: `WO-5228`) → `mcp__atlassian__getJiraIssue`로 조회. `fields`에 반드시 `comment`를 포함해서 코멘트 전체를 함께 가져오세요.
- **메일/텍스트를 붙여넣거나 forward** → 그대로 이슈 내용으로 사용.
- **발신자/제목 등으로 설명만 함** → 해당 채널(Outlook 등)에서 검색해 특정한 뒤 사용자에게 확인.

### 2. 코멘트/스레드 전체를 먼저 읽고 "이미 합의된 방향"을 찾기

Jira 이슈, 특히 오래된 이슈는 최초 설명(description)이 아니라 **코멘트 스레드 안에 실제 기술적 결론이 있는 경우가 많습니다** (담당자 간 왕복 논의 끝에 특정 구현 방식이 합의되기도 하고, 반대로 마지막 코멘트가 아직 답변되지 않은 새 질문일 수도 있습니다). description만 보고 바로 구현에 들어가지 말고:

- 코멘트를 시간순으로 훑어서 이미 합의/확정된 부분이 있는지 확인하세요. 있다면 그 합의를 그대로 구현 근거로 삼습니다 (임의로 다른 접근을 고안하지 마세요).
- 가장 최근 코멘트가 아직 열린 질문이거나 새로운 요청이면, 그 부분은 "미확정"으로 분리해서 다루세요 (아래 5단계 참고).

### 3. SDK 코드 조사

관련 API/함수를 저장소에서 직접 찾습니다 (Grep/Explore 활용):
- 포맷별 API: `src/weboffice/{hwp,word,sheet,slide}/api/`
- 엔진 연동 코어: `src/weboffice/base/engine/core/CoreFunctions.ts`, `OCXCoreFunctions.ts`, `CoreUtils.ts`, `CoreCallbacks.ts`
- 워커: `src/weboffice/base/workers/wasm.worker.ts`

이슈 내용에 언급된 함수명(`IXxx` 형태의 엔진 함수 포함), API 이름, 컴포넌트/다이얼로그 이름을 키워드로 삼으세요.

### 4. 엔진(WASM/C++) 관련 여부 판단

원인이나 해결책이 `IXxx` 엔진 함수 내부 로직에 있는 것으로 보이면 (SDK 쪽 TS 코드만으로는 설명이 안 되는 동작, 엔진 코멘트에 C++ 파일 경로가 언급됨 등) `engine-source-reference` 스킬을 이어서 사용해 엔진 저장소(`PolarisOfficeRnD/PolarisOffice8.0`, `PR/IntX_Weboffice`)를 읽기 전용으로 확인하세요. 엔진 저장소에는 절대 쓰기 작업을 하지 않습니다 — 그쪽 수정이 필요하면 담당 엔진 개발자에게 알리는 선에서 그칩니다.

### 5. 엔진 관련 이슈라면 — 엔진 작업 완료 여부 확인 및 wasm 반영 여부 질문

4단계에서 엔진(WASM/C++) 관련 이슈로 판단했다면, 코드 조사/수정에 들어가기 전에 **반드시 사용자에게 다음을 확인하세요** (Jira 코멘트에 엔진 담당자의 "반영했습니다" 류 메시지가 있어도, 그게 곧 이 SDK 저장소의 wasm 바이너리에 반영됐다는 뜻은 아니므로 임의로 판단하지 마세요):

1. **엔진 쪽 작업이 완료됐는지** 물어보세요 (예: "엔진팀에서 해당 수정이 완료되어 반영 가능한 상태인가요?"). Jira 코멘트에 엔진 개발자가 특정 커밋 해시나 "반영했습니다"를 남긴 경우 참고 정보로 제시하되, 최종 확인은 사용자에게 받으세요.
2. 완료됐다고 답하면, **`wasm-build-update` 스킬을 사용해서 새 wasm 빌드로 교체할지 물어보세요.** 사용자가 원하면 이어서 `wasm-build-update` 스킬을 호출하고, 원치 않으면(예: 아직 다른 이유로 반영 시점이 아님) SDK 쪽 코드(TS) 변경만 먼저 진행하고 wasm 교체는 보류한다고 명확히 알리세요.
3. 엔진 작업이 아직 완료되지 않았다면, SDK 쪽에서 지금 할 수 있는 부분(코멘트에서 이미 합의된 인터페이스/시그니처 등)까지만 진행하고, 실제 동작 검증은 새 wasm 빌드가 들어온 뒤에만 가능하다는 점을 보고에 명시하세요 (임의로 "동작 확인됨"처럼 단정하지 않기).

이 확인을 건너뛰고 wasm 교체까지 자동으로 진행하지 마세요 — wasm 바이너리 교체는 전체 SDK 동작에 영향을 주는 변경이라 항상 사용자 승인이 먼저입니다.

### 6. 구현 범위 판단 — 추측 금지

- 코멘트 스레드에서 **명시적으로 합의된 부분만** 구현하세요. 예: "이렇게 하면 문제 없나요?" → "네 문제없습니다" 처럼 양쪽이 확인한 스니펫/방향은 그대로 반영해도 됩니다.
- 아직 결론이 안 난 질문(예: 새로 제기된 요구사항, 구체적 구현 방식이 안 정해진 요청)은 **임의로 설계해서 구현하지 마세요.** 대신 무엇이 불확실한지 정리해서 사용자에게 보고하고, 다음 행동(엔진팀에 재확인할지, 사용자가 직접 결정할지)을 물어보세요.
- 이 판단 기준은 실제 엔진에서 검증되지 않은 추측을 코드로 단정하지 않기 위함입니다 — 확신이 없는 부분은 "미검증"으로 명확히 표시하세요.

### 7. 코드 수정

Edit/Write로 직접 수정합니다. 가능하면 관련 부분만 빠르게 타입체크하세요:
```
npx tsc --noEmit -p tsconfig.json
```
전체 빌드/테스트까지는 이 스킬의 필수 범위가 아니지만, 변경 범위가 크면 사용자에게 실행 여부를 물어보세요.

### 8. 결과 보고 (Jira/메일에 자동으로 남기지 않음)

**절대 규칙: `mcp__atlassian__addCommentToJiraIssue` 등으로 Jira에 코멘트를 자동으로 남기지 마세요. 메일 답장도 자동 발송하지 마세요.** 무엇을 고쳤는지는 항상 대화창에 텍스트로 요약해서 사용자에게 보고하고, Jira 코멘트나 메일 발송은 사용자가 명시적으로 요청할 때만 (그것도 이 스킬이 아니라 사용자가 직접, 또는 별도 요청 시에만) 진행하세요.

보고에는 다음을 포함하세요:
- 실제로 수정한 파일/내용 (합의된 부분)
- 아직 미확정이라 손대지 않은 부분과, 그 이유
- 엔진 쪽 변경이 필요한데 이 저장소 밖(엔진 소스 저장소)의 일이라 여기서는 반영 불가능한 부분

### 9. 이후 단계 (선택)

- 사용자가 브랜치/커밋/PR을 원하면 `github-workflow` 스킬로 이어가세요.
- wasm 반영 여부는 5단계에서 이미 물어봤어야 합니다. 만약 5단계에서 "아직 미완료"였다가 대화 중간에 사용자가 "이제 엔진 작업 끝났다"고 알려주면, 그 시점에 다시 `wasm-build-update` 스킬 사용 여부를 물어보세요.
