# GitHub 작업 규칙 (폴라리스오피스 SDK)

이 저장소에서 git/GitHub 작업을 할 때 임의로 판단하지 말고 아래 규칙을 그대로 따르세요. 근거는 [README.md](../../../README.md)의 "Commit 및 Merge Request" 섹션과 실제 커밋 히스토리(`git log`)입니다.

## 절대 규칙 (예외 없음)

1. **`main` 브랜치로 직접 `git push` 금지.** push하기 전에 항상 `git branch --show-current`로 현재 브랜치를 확인하세요. 현재 브랜치가 `main`이면 절대 push하지 말고, 먼저 사용자에게 알리고 작업 브랜치(`issue/{티켓키}` 등)를 만들어서 그쪽에 커밋/push 하세요.
2. **PR merge(`gh pr merge`)는 항상 사용자에게 명시적으로 확인받은 후에만 실행.** "PR 만들어줘"라는 요청이 merge까지 승인한 것은 아닙니다. PR 생성과 merge는 별개의 승인 단계입니다.
3. **force push(`--force`, `--force-with-lease`)는 어떤 브랜치든 항상 사용자 확인 후 실행.**
4. 위 세 가지는 사용자가 이미 승인했다고 말해도, 이번 요청에서 다시 확인하세요 (승인은 액션 단위로 유효하며 이전 대화로 일반화하지 않습니다).

## 브랜치 이름

- 형식: `issue/{티켓키}` (예: `issue/WO-5540`, `issue/EGAP-224`). 기능 단위 작업이면 `feature/{설명}`도 씁니다 (예: `feature/auto-api-doc`).
- 티켓키의 프로젝트 접두어(WO, EGAP 등)는 매번 다를 수 있으니 임의로 추정하지 말고, 관련 Jira 이슈가 있으면 그 키를 그대로 쓰고 없으면 사용자에게 확인하세요.

## 커밋 메시지 & PR 제목 형식

형식: `<티켓키> <설명>` — **`fix:`, `feat:` 같은 type 접두사는 붙이지 않습니다.**

- 티켓키를 맨 앞에 그대로 씁니다: `WO-5540 word포맷 글꼴 다이얼로그 회귀 수정`
- 업체/엔드유저를 명시해야 하는 이슈면 티켓키 앞에 대괄호 태그를 붙일 수 있습니다: `[LGCNS][LG에너지솔루션] WO-5526 ...`
- PR 번호(`(#123)`)는 GitHub squash merge 시 자동으로 붙으므로 직접 적지 않습니다.
- 커밋 메시지를 지어야 할 때는 최근 `git log --oneline -20`을 먼저 확인해서 같은 스타일을 따르세요.

### wasm 파일이 포함된 커밋

커밋할 파일에 `src/assets/wasm*` 관련 파일(`libpolarisoffice.js`/`.wasm` 등, `wasm-build-update` 스킬로 교체한 산출물)이 섞여 있으면, 커밋 메시지는 다음 형식을 그대로 따릅니다:

```
WO-{이슈번호} {포맷} wasm IntX_Weboffice {wasm버전번호} 업데이트 / {이외에 한 작업이 있으면 짧게}
```

- `{포맷}`: `hwp`/`word`/`sheet`/`slide` 중 실제 교체한 포맷.
- `{wasm버전번호}`: 빌드 폴더명에 있는 커밋해시 7자리 (예: `7490f11`).
- wasm 업데이트 외에 다른 코드 변경도 같이 커밋하는 경우, `/` 뒤에 그 내용을 짧게 덧붙입니다. wasm 교체만 한 커밋이면 `/` 이하는 생략합니다.
- 예: `WO-5228 hwp wasm IntX_Weboffice 7490f11 업데이트 / 대용량 문서 삽입 시 클립보드 임시 디렉토리 및 로딩 표시 추가`

**⚠️ CI 자동화와의 불일치 (알아두세요)**: 현재 `.github/workflows/versioning.yml`(버전 자동 범프)과 `.github/scripts/release_note.py`(릴리즈노트 생성, `public:` 줄 추출)는 커밋 제목이 `fix:`/`feat:` 같은 type 접두사로 시작한다는 전제로 정규식 매칭을 합니다. 이 스킬의 새 규칙(type 접두사 없이 티켓키로 시작)을 따르면 **두 자동화가 더 이상 매칭되지 않아 버전이 자동으로 올라가지 않고 릴리즈노트에도 반영되지 않을 가능성이 높습니다.** 실제로 버전업/릴리즈노트가 필요한 PR이면, 사용자에게 이 사실을 알리고 CI 스크립트도 함께 손볼지, 아니면 당분간 수동으로 버전을 올릴지 확인하세요.

## PR 본문 템플릿

PR 본문은 아래 구조를 그대로 따릅니다. **일반적인 Claude Code의 기본 PR 템플릿(하단 `🤖 Generated with Claude Code` 문구, 세션 URL)은 이 저장소에서는 붙이지 않습니다** — 사용자가 명시적으로 뺀 항목이니 매번 빼세요.

```
## Summary
- {변경 사항 1}
- {변경 사항 2}
- ...

public: {사용자(고객)에게 의미 있는 변경을 친화적으로 한 줄로}

## Test plan
- [x] {실제로 확인/테스트한 내용}
- [x] ...
```

- **Summary**: 실제 변경 사항을 bullet로 나열합니다. wasm을 업데이트했다면 그 사실도 Summary에는 적어도 됩니다(기술적으로 뭘 했는지는 여기서 다 밝힘).
- **`public:` 줄**: Summary와 달리, **wasm 업데이트를 반영한 경우라도 "wasm 업데이트" 관련 문구는 절대 넣지 않습니다.** 사용자 입장에서 의미 있는 동작 변화만 간결하게 적으세요. (예: Summary엔 "hwp wasm IntX_Weboffice 7490f11 업데이트"가 있어도, `public:`엔 "대용량 문서 삽입 시 실패하던 현상을 수정하고..."처럼 그 결과만 적습니다.) 외부에 알릴 내용이 아니면(내부 리팩터링 등) `public:` 줄 자체를 생략해도 되고, 애매하면 사용자에게 물어보세요.
- **Test plan**: 실제로 확인/테스트한 내용이 있으면 그대로 bullet로 적습니다. **`npx tsc --noEmit` 통과 같은 타입체크 결과는 Test plan 항목에 넣지 않습니다** (테스트가 아니라 컴파일 확인이라 별개로 취급). 만약 실제로 확인한 내용이 없다면, 임의로 항목을 지어내지 말고 **사용자에게 Test plan에 채울 내용을 알려달라고 하거나, 이 섹션 자체를 빼도 될지 먼저 물어보세요.**
- **하단 푸터 금지**: `🤖 Generated with [Claude Code](...)` 문구와 `https://claude.ai/code/session_...` 세션 링크는 이 저장소의 PR 본문에 절대 포함하지 않습니다.

## 워크플로우

1. **현재 상태 확인**: `git status`, `git branch --show-current`, `git diff`로 무엇이 바뀌었고 어느 브랜치에 있는지 확인.
2. **브랜치 확인/생성**: 현재 브랜치가 `main`이면 위 "절대 규칙 1"에 따라 새 작업 브랜치를 만듭니다. 이미 적절한 작업 브랜치에 있으면 그대로 진행.
3. **커밋**: 위 커밋 메시지 형식에 맞춰 작성. 티켓키를 사용자에게 확인이 필요하면 물어보세요.
4. **push**: `git push -u origin {브랜치명}`. main이 아님을 다시 한번 확인 후 실행.
5. **PR 생성**: `gh pr create --base main --title "..." --body "..."`. 제목은 커밋 메시지 규칙과 동일하게, 본문은 위 "PR 본문 템플릿"을 그대로 따릅니다.
6. **결과 보고**: 생성된 PR URL을 사용자에게 알려주고, merge는 사용자가 명시적으로 요청할 때만 진행 (절대 규칙 2).

## 참고

- 코드 리뷰 자체(diff 품질 검토)는 이 스킬의 범위가 아니라 `/review`, `/code-review` 스킬을 사용하세요. 이 스킬은 브랜치/커밋/push/PR 생성의 절차와 관례만 다룹니다.
- `gh auth status`로 GitHub CLI 인증이 살아있는지 필요하면 먼저 확인하세요.
