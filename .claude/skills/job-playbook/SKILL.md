# 프론트엔드 이직 플레이북 Artifact 관리 규칙

이 저장소 사용자가 만들어온 "프론트엔드 이직 플레이북" Artifact를 다시 보여주거나 수정할 때 아래 규칙을 예외 없이 따른다.

## 0. 기본 정보

- URL: `https://claude.ai/code/artifact/6f340716-2415-490b-9f8c-782c1289a257` (제목: "프론트엔드 이직 플레이북")
- 사용자가 "다시 보여줘"라고 하면 이 URL을 그대로 전달한다.
- 내용을 수정해야 하면 **반드시 먼저 `Artifact action:"read"`로 이 URL의 최신 버전을 읽고**, 그 위에서 이어서 수정한다. 기억이나 이전 대화 내용만으로 편집하지 않는다.
- 수정 후에는 **항상 이 같은 URL로 republish**한다(`url` 파라미터에 위 URL 지정). 새 아티팩트를 만들지 않는다.

## 1. 전체 구조

- 상단 탭 3개: **가이드 / 기업 정보 / 트래킹·참고자료**. 탭 버튼은 `flex: 1 1 0`으로 항상 균등 분할되므로 탭이 늘어나도 CSS를 따로 계산할 필요 없다.
- **가이드 탭**: 좌측 sticky(스크롤해도 고정) 사이드바에 7단계 로드맵, 우측 본문은 번호(1~7)를 상위 제목으로 삼아 그 아래에 실제 내용이 하위 섹션(subsection)으로 직접 중첩되는 구조. 단순 링크 목차 방식은 쓰지 않는다.
  - 1단계(이력서 작성·검토): 완료 문구만.
  - 2단계(지원 전략) "지금 당장": 카드 3개(면접스터디 탐색 / 1티어 회사 지원 시작 / 면접 준비), 클릭 시 각각 모달 `modal-study` / `modal-priority` / `modal-answers`가 뜸.
  - 3단계(서류 통과 후 사전 전형): 카드 1개(코딩테스트 대응 전략), 클릭 시 `modal-coding` 모달.
  - 4·5단계(실무진 기술면접 / 임원·컬처핏 면접): "2단계에서 이미 다루고 있습니다." **한 문장만** 있음. 한 번 2단계 가이드로 바로 연결되는 참고 카드를 만들었다가 사용자가 다시 단순 문장으로 되돌렸다 — 다시 카드로 바꾸지 말 것.
  - 6·7단계(레퍼런스체크·처우협상 / 최종합격·입사 결정): 제목만 있고 본문 없음. "세부 가이드 추후 추가 예정" 같은 placeholder 문구를 사용자가 명시적으로 지워달라고 했으니 다시 넣지 말 것. 나중에 채울 때는 다른 단계처럼 카드+모달로 새로 작성.
  - "지원 채널(리멤버/링크드인)" 섹션은 한 번 추가했다가 완전히 삭제됨 — 다시 넣지 말 것.
  - 헤더(`<header class="hero">`)에는 부제 문장과 회색 구분선이 없음 — 다시 넣지 말 것.
- **기업 정보 탭**: 회사를 그룹(빅테크 / 커머스·라이프 플랫폼 / 금융·핀테크 / 게임 / 여행·모빌리티 / 콘텐츠·B2B·AI / 대기업 등)으로 묶고, 각 회사는 `<details class="company-detail">` 아코디언(회사명 클릭 시 펼쳐짐)으로 정리. `summary`에는 회사명 + 가장 눈에 띄는 정보 한 줄(teaser). 본문은 `.info-grid`(dl/dt/dd)로 **채용 주기 / 복지·근무 조건 / 최근 이슈·뉴스 / 기술 스택·팀 문화** 4항목 고정.
- **트래킹·참고자료 탭**: 지원 현황 트래킹 표 + 출처 목록.

## 2. 디자인 시스템 — 새로 만들지 말고 재사용

- 컬러 토큰(`--bg`, `--surface`, `--ink`, `--accent` 등)이 `:root` / `@media (prefers-color-scheme: dark)` / `:root[data-theme="dark"]` 3중 구조로 이미 정의돼 있다. 새 색상은 이 토큰만 사용하고, 라이트/다크 양쪽에 값을 채워 넣는다.
- 폰트: 제목 Spectral, 본문 Public Sans, 라벨·숫자 IBM Plex Mono.
- **카드+모달 패턴**: `.card` + `.card-toggle` 버튼을 클릭하면 `.modal-overlay`/`.modal-dialog`가 뜨고, ESC·배경 클릭·닫기(✕) 버튼으로 닫힌다. 관련 JS는 파일 하단 `<script>`의 `openModal`/`closeModal` 참고.
  - **주의**: `.card-toggle`처럼 버튼 기본 스타일을 리셋할 때 `all: unset` 같은 블랑킷 리셋을 쓰면 `.card`의 border/background/padding/box-shadow가 통째로 사라지는 버그가 실제로 발생했다. 버튼 스타일을 건드릴 때는 border/background/padding/box-shadow를 항상 명시적으로 다시 선언할 것.
- 회사 정보는 `<table>`이 아니라 "회사 블록 하나에 특징+팁(있으면)을 함께 표시"(`.company-block`) 또는 아코디언(`.company-detail`) 구조로 되어 있다 — 표로 되돌리지 말 것. 특징과 팁을 별도 섹션(예: "회사별 스타일 비교" 표 vs "회사별 준비 팁" 목록)으로 다시 분리하지 말 것.

## 3. 콘텐츠 원칙 — 정확성이 최우선

- 회사별 정보(코딩테스트 스타일, 채용 주기, 복지, 최근 이슈, 연봉 등)는 **반드시 실제 웹서치로 확인한 내용만** 작성한다. 확인되지 않으면 지어내지 말고 "확인되지 않음"이라고 명시한다.
- 출처마다 수치가 다르면(연봉 등) 어느 하나를 확정치로 쓰지 말고 "출처마다 편차가 있다"는 점을 그대로 남긴다.
- 정보 섹션에는 "OOOO-MM-DD 기준 확인 — 바뀔 수 있음" 콜아웃을 유지하고, 내용을 갱신할 때마다 그 날짜도 실제 작업일로 바꾼다.
- 회사가 10곳 이상처럼 리서치 범위가 넓을 때는 병렬 fork/subagent로 나눠 조사한 뒤 종합하는 방식이 한 세션에서 효율적이었다(예: 33개 회사를 4개 그룹으로 나눠 동시 조사).
- 위험 신호(구조조정 이력, 재무 위기, 이직률 등)를 발견하면 숨기지 말고 명확히 표시한다(예: 왓챠 기업회생 절차, 크래프톤 평균 근속 1.5년).

## 4. 문서 구조에 대한 일반 선호

이 사용자는 여러 항목을 하나의 가이드/문서로 정리할 때 다음을 선호한다(이 아티팩트뿐 아니라 앞으로 만들 다른 구조화된 문서에도 기본값으로 적용):
- 단순 목차(링크 나열)보다 "번호 제목 아래에 실제 콘텐츠가 직접 중첩"되는 구조.
- 핵심 개요(로드맵 등)는 스크롤해도 계속 보이도록 사이드바 등에 고정.
- 트래킹 표·출처 같은 참고용 자료는 본문과 분리해 탭 등으로 숨김.

## 5. 관련 메모리

- 이 사용자의 이직 준비 진행 상황(로드맵 단계, 확정된 세부 계획 등)은 memory(`project_job_search.md`)에 별도로 기록되어 있다. 그 memory는 진행 상황을, 이 스킬은 아티팩트 자체의 구조·편집 규칙을 담당한다.
