# 채용공고 일일 스카우팅

이 스킬은 **클라우드 예약 루틴**(claude.ai/code/routines)이 매일 실행하는 절차입니다. 실행 주체는 세션 컨텍스트가 전혀 없는 상태로 시작하므로, 아래 내용을 그대로 따르면 됩니다.

## 0. 사용자 프로필 (판단 기준)

- 3년차 프론트엔드 개발자. React, TypeScript, Next.js 중심 경험.
- 목표: **중견기업 이상** 규모 회사로 이직. ([[project_job_search]] 메모리, `job-playbook` 스킬 참고)
- 요구 경력이 **1~6년** 범위인 공고를 우선한다. "Staff", "Principal", "Senior Staff", "Team Leader/리드", "7년 이상" 등 시니어·리드 전용 표현이 명시된 공고는 **제외**한다. 5~6년 요구는 "경계선"으로 분류해 참고용으로만 남긴다 (완전 제외하지 않음 — 실제로 지원해서 통과하는 경우가 있다).
- 완전 신입 전용 공고(대졸 공채 등)는 원칙적으로 낮은 우선순위이지만, 카카오/삼성/SK처럼 "신입크루 공채"가 사실상 초급 경력(1~3년)도 함께 모집하는 경우는 포함한다. 애매하면 상세페이지를 열어 확인한다.
- 직무가 프론트엔드/웹 개발/UI 엔지니어링과 명확히 관련 있어야 한다. "IT 개발 대규모 채용", "테크 부문 채용" 처럼 뭉뚱그려진 공고는 **반드시 상세페이지를 열어** 프론트엔드 직무가 포함되는지 확인한 뒤 포함 여부를 판단한다.
- 재무 위험 신호(구조조정, 자본잠식, 기업회생, 대규모 이직률 등)가 있는 회사는 제외하지 말고 **포함하되 반드시 경고 표시**한다.
- 확인이 안 되는 정보(마감일, 정확한 요구 연차 등)는 지어내지 말고 "확인 안 됨"이라고 쓴다.

## 1. 일반 알고리즘

### 1-1. 접근 순서 (중요: 순서를 바꾸지 말 것)

1. **직접 시도**: 대상 목록에 있는 회사 자체 URL을 WebFetch로 열어본다.
2. **판독**: 실제 회사명·직무명이 텍스트로 보이면 → 그대로 파싱해서 사용. "0개의 포지션", "불러오는 중입니다", 프레임셋만 있는 페이지, 또는 403/빈 응답이면 → SPA이거나 접근 차단된 것이므로 3번으로.
3. **1차 폴백 — 회사명 일반 검색 (사이트 제한 없이)**: `"회사명 프론트엔드 개발자 채용"` 또는 `"회사명 React 개발자 채용 2026"` 같은 쿼리로 **`site:` 제한을 걸지 않고** 검색한다. **이게 핵심이다 — `site:회사도메인`으로만 검색하면 실제로 공고를 놓친다.**
   - **실제 사례**: 현대오토에버는 자체 도메인(`career.hyundai-autoever.com`)이 봇 차단(403)이고, `site:career.hyundai-autoever.com 프론트엔드`로 검색해도 구글 색인이 얕아서 아무것도 안 잡혔다. 그런데 `site:` 없이 "현대오토에버 프론트엔드 채용"으로 검색하니 비즈니스피플(bzpp.co.kr)에 미러링된 실제 공고("[엔터프라이즈 IT] Frontend Developer")가 바로 나왔다. 회사 자체 도메인이 구식이거나 SEO가 약할수록, 사람인·잡코리아·자소서닷컴·비즈니스피플·인크루트·캐치 같은 애그리게이터의 색인이 오히려 더 좋다.
4. **2차 폴백 — `site:` 검색**: 1차로 못 찾았으면 `site:회사도메인 프론트엔드`도 보완적으로 시도한다 (헛수고는 아니고, 회사 도메인이 색인이 잘 되어 있는 경우엔 오히려 더 정확한 결과를 준다 — 카카오페이/카카오모빌리티 등 greetinghr 기반 사이트가 그랬다). 즉 **1차와 2차 둘 다 시도하고, 어느 한쪽에서라도 나오면 채택**한다.
5. **상세 확인**: 후보 URL을 WebFetch로 열어 회사명/직무/요구경력/자격요건/마감일을 확인한다.
6. 목록 페이지가 직접 읽히는 사이트(잡코리아 `stext=` 검색, LinkedIn jobs 검색, 쿠팡 coupang.jobs, 두나무 dunamu.com/careers/jobs 등)는 그대로 목록에서 여러 건을 한 번에 훑을 수 있다 — 이런 사이트는 우선적으로 활용한다.

### 1-1a. 검증 없이는 절대 "발견"으로 올리지 않는다 (매우 중요)

실제로 아래 두 가지 사고가 났었다:
- **WebSearch의 요약 문장을 그대로 믿었다가 틀린 사례**: "네이버파이낸셜 프론트엔드 개발자(2년+)", "뱅크샐러드 Web Front Engineer"는 WebSearch가 생성한 요약 문장에는 있었지만, 실제로 그 도메인을 `site:` 검색으로 다시 확인하니 **근거가 되는 실제 페이지 자체가 존재하지 않았다.** WebSearch의 서술형 요약은 검색 결과를 잘못 종합하거나 다른 회사 정보와 섞을 수 있다 — **요약 문장은 "찾아볼 단서"일 뿐, 그 자체로 확인된 사실이 아니다.**
- **마감/폐기된 공고를 그대로 올린 사례**: 토스랩(잔디) 공고는 2021년 마감, 컨비니언스 공고는 2023년 마감, 현대오토에버·펄어비스 공고는 명시적으로 "본 공고는 마감되었습니다"라고 표시돼 있었는데 확인 없이 "발견"으로 올렸다. 카카오헬스케어라고 올렸던 링크는 아예 채용공고가 아니라 **직원 인터뷰 후기 페이지**였다.

그래서 "발견"으로 분류하려면 **반드시 다음을 만족해야 한다**:

1. **실제 URL을 WebFetch로 직접 열어서 확인**한다 — WebSearch 요약 문장만 보고 판단하지 않는다.
2. 그 페이지가 **진짜 채용공고 상세**인지 확인한다 (블로그/인터뷰/후기/회사소개 페이지가 아닌지 — 제목만 보고 넘겨짚지 말고 본문에 자격요건·모집 안내 같은 채용공고 특유의 구조가 있는지 본다).
3. **마감 여부를 명시적으로 확인**한다 — "마감되었습니다", "채용이 종료되었습니다", "지원이 마감된 공고입니다" 같은 문구가 있으면 즉시 제외. 마감일이 명시돼 있으면 오늘 날짜와 비교한다. "상시채용"이라고 명시돼 있으면 유효로 간주한다. **아무 날짜/상태 표시도 없으면 "발견"이 아니라 "경계선"이나 별도 캡션("마감 여부 확인 안 됨")으로 낮춰서 보고한다** — 확실하지 않은 걸 확신 있게 보고하지 않는다.
4. 회사의 **현재 목록 페이지를 직접 렌더링해서 얻은 결과**(예: 당근 division 필터 페이지가 오늘 실제로 6건을 보여준 경우)는 그 자체로 "오늘 기준 살아있음"이 증명된 것이라 신뢰도가 가장 높다. 반면 **검색으로 찾은 개별 URL 하나**(원티드 wd/<id>, greetinghr /o/<id>, bzpp.co.kr 등)는 과거에 색인된 페이지일 수 있으니 위 1~3단계를 반드시 거친다.

### 1-2. 판정 결과 3종류 — 반드시 이 중 하나로 명확히 분류할 것

한 회사를 확인했으면 아래 세 가지 중 **정확히 하나**의 상태로 기록한다. "확인 못함"이라는 애매한 상태를 남기지 않는다 — 1~4단계를 다 시도했는데도 못 찾았다면 그것도 "확인 완료, 결과 없음"이지 "확인 못함"이 아니다.

- **✅ 발견됨** — 조건에 맞는 공고를 실제로 찾음.
- **◻ 확인함 · 해당 없음** — 1차·2차 폴백을 모두 시도했지만 현재 조건에 맞는 프론트엔드 공고가 없음. (예: 두나무 — 오늘 목록에 백엔드/보안/법무만 있고 프론트엔드가 아예 없어서 "해당 없음"으로 정직하게 처리하는 게 맞다. 이건 실패가 아니라 유효한 결과다.)
- **⛔ 접근 실패** — 403 차단, 타임아웃, 검색으로도 후보를 전혀 못 찾은 경우. 이건 "해당 없음"과 다르다 — 다음 회차에 다른 방법(다른 검색어, 다른 애그리게이터)으로 재시도해야 함을 뜻한다.

디스코드로 보내는 요약과 아티팩트 리포트 모두 이 세 카테고리를 구분해서 보여준다. "오늘 확인 못한 채널"처럼 뭉뚱그린 카테고리는 쓰지 않는다.

**이 3종류는 "발견 여부"를 나누는 축이고, 별개로 "적합도" 축이 하나 더 있다.** `✅ 발견됨`에 속한 공고는 0장 프로필 기준에 따라 다시 **추천**(1~6년, 프론트엔드 명확) / **경계선**(5~6년 상단이거나 표기가 애매함) / **제외**(7년 이상, Staff/리드급)로 나눈다. `◻ 확인함·해당없음`과 `⛔ 접근실패`는 애초에 "발견됨"이 아니므로 추천/경계선/제외 분류 대상이 아니다.

### 1-3. 놓치는 공고를 줄이는 팁

- 자체 채용페이지가 있는 회사도 **애그리게이터(원티드/사람인/잡코리아/LinkedIn) 교차 확인을 반드시 병행**한다. 회사 자체 페이지에만 올라오고 애그리게이터엔 없는 경우, 반대로 애그리게이터에만 올라오고 자체 페이지 갱신이 늦는 경우가 둘 다 있다 (CJ올리브영은 자체 검색으론 안 잡혔는데 LinkedIn에서 3건이 잡힌 사례가 실제로 있었다).
- 여러 회사가 같은 ATS(채용솔루션)를 쓴다 — GreetingHR(`*.career.greetinghr.com`), Greenhouse(`job-boards.greenhouse.io/*`), Recruiter.co.kr, RoundHR 등. 한 회사에서 되는/안 되는 방식이 같은 ATS를 쓰는 다른 회사에도 그대로 적용될 가능성이 높다.
- LinkedIn 채용 검색은 로그인 없이도 실제로 텍스트가 잘 읽히고, 외국계·글로벌 지사를 잡아내는 데 특히 유용하다. 하루 1회 정도의 가벼운 조회로 제한할 것.
- 잡플래닛은 채용공고보다 기업 리뷰용 사이트에 가까워 공고 수가 적다 — 보조 채널로만 가볍게 확인.
- 자소서닷컴(jasoseol.com)은 신입/대기업 공채 중심이지만, 실제로 경력직 공고 미러링도 꽤 있다 (현대오토에버 사례) — 무시하지 말 것.
- **신규 보조 애그리게이터** (오늘 발견, 회사 자체 페이지가 막혀 있을 때 특히 유용): 비즈니스피플(`bzpp.co.kr`), 인크루트(`incruit.com`), 캐치(`catch.co.kr`).
- 로그인 후에만 보이는 "맞춤 추천" 피드는 어떤 사이트에서도 접근할 수 없다 — 공개 검색/목록 결과만 대상으로 한다.

## 2. 중복 공고 처리

같은 공고가 회사 자체 페이지·원티드·사람인·잡코리아·LinkedIn 등 여러 채널에 동시에 올라오는 경우가 매우 흔하다. **같은 공고를 채널 수만큼 여러 번 보여주지 않는다.**

- **동일 공고 판단 기준**: 회사명이 같고 + 직무명의 핵심 키워드가 같거나(예: "프론트엔드", "Frontend Engineer") + (가능하면) 마감일·근무지가 일치하면 같은 공고로 간주한다.
- **병합 방법**: 하나의 항목으로 합치고, `발견 채널` 태그에 발견된 모든 채널을 나열한다 (예: `발견 채널: 자체 페이지, 원티드, 잡코리아`). 링크는 가장 정보가 많은 출처(보통 회사 자체 페이지 > 원티드 상세 > 애그리게이터 순)를 대표 링크로 쓰고, 나머지는 "다른 곳에서도 확인: 원티드, 잡코리아"처럼 짧게 덧붙인다.
- 같은 회사가 **여러 개의 서로 다른 포지션**을 올린 경우(예: CJ올리브영의 검색플랫폼/엔터프라이즈/커머스 3건)는 중복이 아니라 각각 별개 항목이다 — 직무명이 명확히 다르면 합치지 않는다.

## 3. 대상 목록

각 회사 옆의 상태는 **가장 최근 확인 결과**다. 매 실행마다 다시 확인하고 상태를 최신화한다. ✅=발견됨, ◻=확인함·해당없음, ⛔=접근차단, ❓=아직 제대로 확인 안 됨(다음 회차에 반드시 1차·2차 폴백까지 시도할 것).

### 3-1. 채용 애그리게이터 (매일 필수 스윕)

| 사이트 | 방법 | 상태 |

| LinkedIn | `https://www.linkedin.com/jobs/search/?keywords=<키워드>&location=Seoul` | ✅ 직접 판독 확인됨 |

| 사람인 | 목록은 SPA → 일반검색/`site:saramin.co.kr` 검색 + 상세 `zf_user/jobs/view?rec_idx=...` | ✅ |

## 4. 플랫폼별 실전 팁

- **잡코리아**: `Search/?stext=<키워드>` 형태 URL로 직접 검색하면 목록이 텍스트로 바로 보인다. 로그인/JS 불필요.
- **LinkedIn**: `jobs/search/?keywords=...&location=Seoul` 형태로 검색하면 공개 결과가 텍스트로 잘 읽힌다. 로그인 후 개인화 피드는 접근 불가.
- **원티드**: 목록·검색 페이지(`wanted.co.kr/wdlist/...`)는 SPA라 못 읽지만, 개별 공고 상세(`wanted.co.kr/wd/<숫자>`)는 SEO 때문에 서버에서 렌더링돼 있어 WebFetch로 바로 읽힌다.
- **사람인**: 마찬가지로 목록은 SPA, 상세(`zf_user/jobs/view?rec_idx=...` 또는 `.../relay/view?...`)는 읽힌다.
- **GreetingHR 기반 사이트** (`*.career.greetinghr.com` — SSG, 카카오페이, 카카오모빌리티, 무신사, 뱅크샐러드, 11번가, 여기어때, 컬리 등): 개별 공고는 `.../o/<숫자>` 또는 `.../<슬러그>` 형태 URL을 가지며, `site:도메인 키워드` 검색으로 개별 공고가 잘 잡히는 편이었다 (컬리만 예외적으로 403 차단).
- **당근**: `careers.daangn.com/jobs/?division=...` 필터 파라미터가 있지만 실제로는 필터링이 완전히 적용되지 않는 것처럼 보일 때가 있다 — division 필터를 믿지 말고 결과 안에서 직무명을 직접 확인할 것.
- **토스**: 전 계열사(토스/토스뱅크/토스증권/토스페이먼츠/토스인슈어런스)가 `toss.im/career/jobs` 한 페이지에서 필터로 관리되는데, 이 페이지 자체는 완전한 SPA다. `site:toss.im/career` 검색은 실제로 매우 잘 작동해서 마감일까지 나온다 — 이 사이트는 site: 검색이 일반검색보다 오히려 낫다.
- **쿠팡**: `coupang.jobs`의 검색 결과 페이지 자체가 서버에서 렌더링돼 목록을 바로 읽을 수 있다. 다만 `search=front-end` 필터를 걸어도 결과에 무관한 직무(보안, PM 등)가 섞여 나오니 제목을 반드시 다시 확인할 것. 시니어(Staff/Senior/Principal) 비중이 매우 높은 회사다.
- **두나무**: `dunamu.com/careers/jobs`도 목록이 바로 읽힌다.
- **자체 도메인이 낡았거나(프레임셋 등) 봇을 차단하는 회사** (CJ그룹 통합 포털 `recruit.cj.net`, 현대오토에버, 현대캐피탈 등): 회사 도메인에서 직접 찾으려 하지 말고 **처음부터 일반검색(회사명+직무 키워드, site: 제한 없이)으로 시작**하는 게 훨씬 빠르다. 이 회사들은 사람인·잡코리아·자소서닷컴·비즈니스피플에 공고를 활발히 미러링한다.
- **네이버/카카오 계열**: 본사·대형 계열사는 자체 포털이 SPA인 경우가 대부분이라, 계열사별로 일반검색을 따로 돌리는 게 효율적이다 (예: "카카오헬스케어 프론트엔드", "네이버파이낸셜 프론트엔드"를 각각 검색 — "네이버 프론트엔드"처럼 본사명으로만 검색하면 계열사 공고에 묻혀서 잘 안 보일 수 있다).

## 5. 애매한 공고 판단법

"경력채용", "대규모 채용", "OO부문 채용", "테크 채용" 처럼 직무가 특정되지 않은 공고를 만나면:
1. 상세페이지를 반드시 연다.
2. 모집 직무/부문 목록에 프론트엔드/웹/UI 관련 항목이 있는지 확인한다 (React, Vue, TypeScript, SPA, 웹 퍼블리싱, UI 엔지니어 등의 키워드).
3. 있다면 그 항목만 골라서 포함하고, 나머지 무관한 직무는 무시한다.
4. 이런 대규모/그룹 공채는 보통 지원 시 직무를 선택하는 구조이니, 최종 보고에도 "프론트엔드 트랙으로 지원" 같이 명시한다.

## 6. 출력 형식 — 아티팩트(HTML 리포트)로 정리한다

찾은 공고는 텍스트로 끝내지 않고, **Artifact 도구로 리포트 페이지를 발행/갱신**한 뒤 그 링크를 디스코드로 보낸다.

- 리포트 URL: `https://claude.ai/code/artifact/756148a8-e1f5-4d7b-9002-e2070c488a1e` (제목: "채용 스카우팅 리포트")
- **반드시 먼저 `Artifact action:"read"`로 이 URL의 최신 버전(디자인 시스템·구조)을 읽고**, 그 위에서 그날의 데이터만 교체한다. 디자인(색 토큰, 폰트, 카드/태그 스타일, 라이트·다크 테마 구조)은 그대로 유지하고 절대 새로 디자인하지 않는다.
- 페이지 구조: 상단 통계(확인 채널 수 / 발견·검증됨 / 경계선 / 제외 / 재검증 필요 건수 — 5개) → **오늘의 추천 공고**(카드, 요구경력·마감일·발견채널 태그 — 중복이면 채널을 여러 개 나열, 2장 기준으로 병합 — + 적합도 한 줄 + 원문 링크) → **경계선 참고**(조건에 살짝 벗어나는 것 + 이유) → **제외된 공고**(판단 근거) → **확인함·해당 없음**(정직하게, "공고가 없었다"는 것도 유효한 결과임을 보여줌) → **접근 실패·재시도 필요**(⛔ 차단된 곳, 다음 회차 계획) → 하단에 방법론 한 줄과 회차 날짜.
- "오늘 확인하지 못한 채널"이라는 애매한 섹션은 쓰지 않는다 — 1장 1-2절의 세 카테고리(발견/해당없음/접근실패)로만 나눈다.
- 새로 조건에 맞는 공고가 없으면 추천 섹션에 "오늘은 조건에 맞는 새 공고를 찾지 못했습니다"라고 짧게 쓰고 나머지 섹션은 평소대로 채운다.
- **수정 후 항상 같은 URL로 republish**한다(`url` 파라미터에 위 URL 지정, `favicon`은 생략해서 기존 아이콘 유지). 새 아티팩트를 만들지 않는다.

## 7. 디스코드 전송

**중요**: 디스코드 웹훅 URL은 이 스킬 파일(공개 GitHub 저장소)에 저장하지 않는다. 실행 시 루틴의 프롬프트(사용자 메시지)에 담겨 전달되니, 그 값을 사용한다. (반대로 위 아티팩트 URL은 비밀이 아니므로 이 파일에 그대로 적어둔다.)

아티팩트 리포트를 완전히 발행한 뒤, **짧은 요약 + 링크만** 디스코드로 보낸다 (전체 내용을 디스코드 메시지에 다시 쓰지 않는다):

1. Write 도구로 payload를 JSON 파일(`/tmp/discord_payload.json` 등)로 만든다. 형식: `{"content": "**YYYY-MM-DD 채용 스카우팅 결과** — 발견 N건 / 경계 N건 / 제외 N건\nhttps://claude.ai/code/artifact/756148a8-e1f5-4d7b-9002-e2070c488a1e"}`. 개행은 JSON 문자열 안에서 `\n`으로 이스케이프해야 하므로, 셸에서 직접 조립하지 말고 Write 도구로 파일을 작성해 이스케이프 문제를 피한다.
2. 전송 커맨드: `curl -sS -H "Content-Type: application/json" -X POST -d @/tmp/discord_payload.json "<웹훅 URL>"`
3. 전송 후 실제로 204 No Content가 왔는지 확인하고, 실패하면(4xx/5xx) 에러 내용을 최종 보고에 남긴다.
